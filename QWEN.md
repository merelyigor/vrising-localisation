# Правила проєкту — vrising-localisation

## §1 Пріоритет правил [MUST]
1. Інструкції користувача в поточному завданні.
2. Безпекові/юридичні обмеження.
3. Локальні правила проєкту (`AGENTS.md`, `.cursorrules`, `CLAUDE.md`).
4. Загальні best practices.

Якщо є конфлікт правил — явно зафіксувати і запитати рішення власника.

## §2 Мова і комунікація [MUST]
- §2.1 Комунікація з користувачем, документація, коментарі, commit messages — українською.
- §2.2 Код, ідентифікатори, логи, тексти помилок не перекладати.
- §2.3 Відповідати коротко, по суті, з конкретними кроками.
- §2.4 Явно позначати припущення, ризики, обмеження.
- §2.5 Асистент виконує команди сам, не перекладає кроки на користувача.

## §3 Контекст і архітектура [MUST]
- §3.1 Інструмент українізації V Rising: PHP-бекенд (`core/*.php`) + JS/SCSS фронт, зібраний Webpack (`webpack.config.js`, `src/*` → `public/assets/*`).
- §3.2 Джерело правди для перекладів — **Crowdin** (проєкт `PROJECT_ID = 519216`, `core/all-include.php`), не локальна БД: цей проєкт БД не використовує взагалі.
- §3.3 `core/RequestsCrowdin.php` (`RequestsCrowdin`) — обгортка над `crowdin/crowdin-api-client`; `core/api.core.php` — тонкий HTTP-роутер над GET-параметрами, що викликає цю обгортку.
- §3.4 `json-local/` — локальний кеш/експорт перекладів у JSON; `save-json.php` приймає завантаження файлу і БЕЗУМОВНО перезаписує файл із тим самим імʼям.
- §3.5 Local: `localisation-vrising-ua.eremenko.dev`. Production: `localisation-vrising-ua.eremenko.top`.

## §4 MCP/інструменти [ADAPT]
- §4.1 Serena primary path для refactoring/references/великих класів; route-параметри,
  Webpack і конфіги — `rg` + targeted reads + execution flow.
- §4.2 Перед semantic task: readiness probe; при збої перевірити/повторно активувати
  `.serena/project.yml` один раз і виправити repo-local конфіг у Git. Global
  blocker або дві невдалі спроби: без silent fallback, потрібен дозвіл. Serena
  не замінює `php -l`, build і runtime checks.
- §4.3 **Context7 (зовнішня документація)**: використовувати лише коли відповідь залежить
  від API зовнішньої бібліотеки/фреймворку і ризик вигаданого API/параметра реальний.
  Джерело істини №1 — код проєкту і фактично встановлені версії (lock-файли,
  `vendor/`, `node_modules/`); при розбіжності діє встановлений код, не документація.
  Для Docker/Nginx/bash/`.env`/YAML і того, що вже є в репозиторії, canonical path —
  `rg` + targeted reads. Сервер зареєстрований глобально в клієнтах, тому проєктний
  конфіг його не дублює, а `CONTEXT7_API_KEY` не хардкодиться.
- §4.4 **Playwright (тільки web/UI)**: перевірка сторінки після змін, репродукція UI-баґу,
  console/network errors, скріншоти, форми й навігація, smoke-тест admin/frontend. Для
  backend, Docker, bash, SQL і аналізу коду не застосовувати — там він лише додає tool
  schemas, з'їдає контекст і провокує хибні tool calls. Спершу дешевша перевірка
  (HTTP-статус, логи, тести, статичний аналіз); браузер — коли факт інакше не отримати.
  За замовчуванням ВИМКНЕНИЙ і працює лише в агенті `browser-test`: Claude Code —
  inline `mcpServers` у frontmatter агента; OpenCode — `mcp.playwright.enabled` на час
  UI-роботи, `playwright*` дозволений тільки цьому агентові; Codex — `enabled = false`
  поза UI-задачею. Профіль `--isolated`, тому логін робити формою в межах сесії.
  Production у браузері — read-only; форми, збереження, публікації й адмін-дії на
  проді — лише з явним дозволом. Браузер не замінює тести: причину баґу підтверджувати
  кодом і логами.
- §4.5 **Shadcn/UI**: стек (PHP + vanilla frontend) не є сумісним React/Tailwind
  UI-контуром, тому Shadcn тут не застосовується — canonical UI system лишається наявна.
  Розглядати Shadcn лише після узгодженого плану інтеграції, без паралельної design
  system.
- §4.6 **OpenCode Zen / безкоштовні моделі**: при питаннях щодо вибору моделі, лімітів,
  безпеки або порівняння — спочатку інфра-документація
  `merely-server-infra/docs/OPENCODE-ZEN-MODELS.md`,
  потім зовнішні джерела.

## §5 Crowdin API [MUST]
- §5.1 Crowdin — зовнішній rate-limited сервіс; не робити масові/циклічні запити без потреби, кешувати результат локально (`json-local/`), а не перезапитувати те саме повторно.
- §5.2 Токен доступу до Crowdin (`API_KEY` у `core/all-include.php`) НЕ хардкодити далі: нову або змінену інтеграцію писати проти ENV-змінної, а не проти константи у файлі. Наявний хардкод — відомий борг, не приклад для копіювання.
- §5.3 Не змінювати `usernames_translation_priority` (`RequestsCrowdin.php`) без явного запиту — впливає на пріоритет чиїх перекладів показує інструмент.

## §6 Безпека [MUST]
- §6.1 Не хардкодити нові секрети/ключі/паролі; існуючі — не копіювати в інші файли.
- §6.2 Завантаження файлів (`save-json.php`) — за потреби змін обовʼязково додати перевірку розширення/типу і розміру; поточна реалізація приймає будь-який файл і перезаписує без перевірки.
- §6.3 Валідація/санітизація зовнішніх входів (GET-параметри `api.core.php`) обовʼязкова для нового коду.

## §7 Production і деструктивні дії [MUST]
- §7.1 Production — тільки read-only без явного дозволу.
- §7.2 `git commit`/`git push`, видалення файлів/директорій — тільки з явним дозволом.
- §7.3 SSH на прод — тільки `ssh_with_password_fallback`, не прямий `ssh`/`sshpass`.
- §7.4 Правильний шлях змін: локально → перевірка → commit → GitHub Actions deploy.
- §7.5 Нову ENV-змінну — в обидва `docker/.env.local`/`.env.prod`.

## §8 Валідація після змін [MUST]
- §8.1 Перед браузером — дешевша перевірка: `php -l`, логи, прямі запити до Crowdin API, статичний аналіз.
- §8.2 Для змінених PHP-файлів: мінімум `php -l`.
- §8.3 Для JS/SCSS змін: збірка через `NODE_BUILD_COMMAND` (`npm install --include=dev && npx webpack-cli --mode production`).
- §8.4 Якщо перевірку не вдалось виконати — явно вказати це у фінальній відповіді.

### SEO impact gate
- §8.5 Після будь-яких змін виконувати короткий SEO-triage: `N/A`, `possible impact`
  або `direct impact`; повний аудит потрібен лише за фактичного впливу.
- §8.6 У фіналі: `SEO-check: N/A | Passed | Fixed` з короткими доказами.

## §9 Документація [MUST]
- §9.1 Якщо змінюється поведінка інтеграції з Crowdin, формат `json-local/` або API-роути — оновлювати `README.md` цього проєкту.

## §10 Definition of Done [MUST]
1. Реалізовано цільову поведінку.
2. Виконано релевантні перевірки або зафіксовано причину пропуску.
3. Оновлено docs, якщо релевантно.
4. Зафіксовано ризики/компроміси, якщо є.

## §11 ✍️ ПРАВИЛО ЕВОЛЮЦІЇ ЦЬОГО ФАЙЛУ
Нові правила додаються так, щоб одночасно зберігати:
1. **100% змістовність та однозначність вимог**;
2. **мінімально необхідний обсяг тексту** (без дублювання, без повторів прикладів, без зайвої риторики);
3. **структурну компактність** (короткі норми, згруповані в секції, без роздування файлу).

При оновленні правил заборонено:
- §11.1 видаляти чинні вимоги без явного рішення користувача;
- §11.2 додавати дублікати правил у різних секціях;
- §11.3 замінювати норми на розмиті формулювання, що знижують однозначність.
- §11.4 Пряму вимогу власника щодо правил вносити в цій задачі; сталі інваріанти Crowdin,
  форматів локалізації чи API фіксувати без разових перекладацьких даних і секретів.

## §12 🪞 СИНХРОНІЗАЦІЯ `AGENTS.md`, `.cursorrules` І `CLAUDE.md`
- §12.1 `AGENTS.md`, `.cursorrules` і `CLAUDE.md` мають бути ідентичними.
- §12.2 Кожну зміну правил дублювати в усі три файли в одному оновленні.
- §12.3 Після змін перевіряти: `cmp -s AGENTS.md .cursorrules && cmp -s AGENTS.md CLAUDE.md`.

## §13 Нумерація правил §N / §N.M
- §13.1 Секція має номер `§N` у заголовку, кожен top-level пункт — `§N.M`. **Номер сталий і
  ніколи не змінюється**: нове правило отримує НАСТУПНИЙ ВІЛЬНИЙ номер, а не той, що
  відповідає його позиції; видалене правило лишає дірку, яку не заповнюють.
  Перенумерації не буває, тому жодного інструмента не потрібно — правила самодостатні.
- §13.2 Наслідок: номери можуть іти не по порядку зверху вниз. Це свідома ціна за те, що
  номер завжди означає те саме правило, а посилання на нього не застарівають.
- §13.3 Посилатися на правило лише як `§N` / `§N.M`, не «розділ N» і не назвою секції: назви
  змінюються, а текстові посилання мовчки застарівають. Посилання на розділ ЗОВНІШНЬОГО
  документа обов'язково називати цей документ.
- §13.4 Дублікат номера, пункт із чужим номером секції й посилання на неіснуюче правило —
  помилка, яку виправляють одразу.
## §14 PhpStorm false positive та IDE-конфігурація

- Якщо користувач передає warning/error зі скріншота PhpStorm, агент спочатку перевіряє фактичну причину за кодом, конфігурацією, usages/call sites і доступними validator/тестами.
- Реальні помилки, critical warnings, broken references та runtime/security/data-ризики обов’язково виправляються; їх не можна приховувати через `.idea`.
- Підтверджений false positive або безпечний допустимий випадок виправляється вузьким project-level правилом у versioned `.idea` (наприклад `filetypes.xml` або `inspectionProfiles/Project_Default.xml`), а не локальним ручним override PhpStorm.
- Не вимикати глобально inspections, знижувати severity для всього класу проблем або обходити реальні pre-commit/CI/test/lint/static-analysis/security gates.
- Після зміни `.idea` перевірити XML, diff і affected file/problem. Синхронізувати це правило в `AGENTS.md`, `.cursorrules`, `CLAUDE.md` і `QWEN.md`; вони мають залишатися ідентичними.

## §15 Відповідь у чаті: обовʼязковий блок «Що далі»
- §15.1 Кожна відповідь із виконаною роботою завершується блоком «Що далі». Він містить фактичний стан: готово, готово частково або заблоковано.
- §15.2 Далі навести 2-4 варіанти дій; перший позначити рекомендованим. Для кожного коротко вказати дію, орієнтовний час, ризик і користь.
- §15.3 Окремо прямо вказати, що потрібно від власника: рішення, дані, запуск гри, дозвіл на commit або нічого.
- §15.4 Якщо роботу не завершено, запропонувати наступний конкретний крок, а не лише описати проблему.
- §15.5 У блоці пояснювати, що зміниться для користувача або роботи, без зайвих технічних деталей і переліку файлів.
- §15.6 Результати перевірок і обов'язкові для задачі гейти зазначати перед блоком «Що далі», який має бути останнім у відповіді.
