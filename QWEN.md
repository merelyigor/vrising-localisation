# Правила проєкту — vrising-localisation

## 1) Пріоритет правил [MUST]
1. Інструкції користувача в поточному завданні.
2. Безпекові/юридичні обмеження.
3. Локальні правила проєкту (`AGENTS.md`, `.cursorrules`, `CLAUDE.md`).
4. Загальні best practices.

Якщо є конфлікт правил — явно зафіксувати і запитати рішення власника.

## 2) Мова і комунікація [MUST]
- Комунікація з користувачем, документація, коментарі, commit messages — українською.
- Код, ідентифікатори, логи, тексти помилок не перекладати.
- Відповідати коротко, по суті, з конкретними кроками.
- Явно позначати припущення, ризики, обмеження.
- Асистент виконує команди сам, не перекладає кроки на користувача.

## 3) Контекст і архітектура [MUST]
- Інструмент українізації V Rising: PHP-бекенд (`core/*.php`) + JS/SCSS фронт, зібраний Webpack (`webpack.config.js`, `src/*` → `public/assets/*`).
- Джерело правди для перекладів — **Crowdin** (проєкт `PROJECT_ID = 519216`, `core/all-include.php`), не локальна БД: цей проєкт БД не використовує взагалі.
- `core/RequestsCrowdin.php` (`RequestsCrowdin`) — обгортка над `crowdin/crowdin-api-client`; `core/api.core.php` — тонкий HTTP-роутер над GET-параметрами, що викликає цю обгортку.
- `json-local/` — локальний кеш/експорт перекладів у JSON; `save-json.php` приймає завантаження файлу і БЕЗУМОВНО перезаписує файл із тим самим імʼям.
- Local: `localisation-vrising-ua.eremenko.dev`. Production: `localisation-vrising-ua.eremenko.top`.

## 4) MCP/інструменти [ADAPT]
- Serena primary path для refactoring/references/великих класів; route-параметри,
  Webpack і конфіги — `rg` + targeted reads + execution flow.
- Перед semantic task: readiness probe; при збої перевірити/повторно активувати
  `.serena/project.yml` один раз і виправити repo-local конфіг у Git. Global
  blocker або дві невдалі спроби: без silent fallback, потрібен дозвіл. Serena
  не замінює `php -l`, build і runtime checks.
- **Context7 (зовнішня документація)**: використовувати лише коли відповідь залежить
  від API зовнішньої бібліотеки/фреймворку і ризик вигаданого API/параметра реальний.
  Джерело істини №1 — код проєкту і фактично встановлені версії (lock-файли,
  `vendor/`, `node_modules/`); при розбіжності діє встановлений код, не документація.
  Для Docker/Nginx/bash/`.env`/YAML і того, що вже є в репозиторії, canonical path —
  `rg` + targeted reads. Сервер зареєстрований глобально в клієнтах, тому проєктний
  конфіг його не дублює, а `CONTEXT7_API_KEY` не хардкодиться.
- **Playwright (тільки web/UI)**: перевірка сторінки після змін, репродукція UI-баґу,
  console/network errors, скріншоти, форми й навігація, smoke-тест admin/frontend. Для
  backend, Docker, bash, SQL і аналізу коду не застосовувати — там він лише додає tool
  schemas, з'їдає контекст і провокує хибні tool calls. Спершу дешевша перевірка
  (HTTP-статус, логи, тести, статичний аналіз); браузер — коли факт інакше не отримати.
  За замовчуванням ВИМКНЕНИЙ і працює лише в агенті `browser-test`: Claude Code —
  inline `mcpServers` у frontmatter агента; OpenCode — `mcp.playwright.enabled` на час
  UI-роботи, `playwright*` дозволений тільки цьому агентові; Codex — `enabled = false`
  поза UI-задачею. Профіль `--isolated`, тому логін робити формою в межах сесії.
  Production у браузері — read-only; форми, збереження, публікації й адмін-дії на
  проді — лише з явним дозволом. Браузер не замінює тести: причину баґу підтверджувати
  кодом і логами.
- **Shadcn/UI**: стек (PHP + vanilla frontend) не є сумісним React/Tailwind
  UI-контуром, тому Shadcn тут не застосовується — canonical UI system лишається наявна.
  Розглядати Shadcn лише після узгодженого плану інтеграції, без паралельної design
  system.
- **OpenCode Zen / безкоштовні моделі**: при питаннях щодо вибору моделі, лімітів,
  безпеки або порівняння — спочатку інфра-документація
  `merely-server-infra/docs/OPENCODE-ZEN-MODELS.md`,
  потім зовнішні джерела.

## 5) Crowdin API [MUST]
- Crowdin — зовнішній rate-limited сервіс; не робити масові/циклічні запити без потреби, кешувати результат локально (`json-local/`), а не перезапитувати те саме повторно.
- Токен доступу до Crowdin (`API_KEY` у `core/all-include.php`) НЕ хардкодити далі: нову або змінену інтеграцію писати проти ENV-змінної, а не проти константи у файлі. Наявний хардкод — відомий борг, не приклад для копіювання.
- Не змінювати `usernames_translation_priority` (`RequestsCrowdin.php`) без явного запиту — впливає на пріоритет чиїх перекладів показує інструмент.

## 6) Безпека [MUST]
- Не хардкодити нові секрети/ключі/паролі; існуючі — не копіювати в інші файли.
- Завантаження файлів (`save-json.php`) — за потреби змін обовʼязково додати перевірку розширення/типу і розміру; поточна реалізація приймає будь-який файл і перезаписує без перевірки.
- Валідація/санітизація зовнішніх входів (GET-параметри `api.core.php`) обовʼязкова для нового коду.

## 7) Production і деструктивні дії [MUST]
- Production — тільки read-only без явного дозволу.
- `git commit`/`git push`, видалення файлів/директорій — тільки з явним дозволом.
- SSH на прод — тільки `ssh_with_password_fallback`, не прямий `ssh`/`sshpass`.
- Правильний шлях змін: локально → перевірка → commit → GitHub Actions deploy.
- Нову ENV-змінну — в обидва `docker/.env.local`/`.env.prod`.

## 8) Валідація після змін [MUST]
- Перед браузером — дешевша перевірка: `php -l`, логи, прямі запити до Crowdin API, статичний аналіз.
- Для змінених PHP-файлів: мінімум `php -l`.
- Для JS/SCSS змін: збірка через `NODE_BUILD_COMMAND` (`npm install --include=dev && npx webpack-cli --mode production`).
- Якщо перевірку не вдалось виконати — явно вказати це у фінальній відповіді.

### SEO impact gate
- Після будь-яких змін виконувати короткий SEO-triage: `N/A`, `possible impact`
  або `direct impact`; повний аудит потрібен лише за фактичного впливу.
- У фіналі: `SEO-check: N/A | Passed | Fixed` з короткими доказами.

## 9) Документація [MUST]
- Якщо змінюється поведінка інтеграції з Crowdin, формат `json-local/` або API-роути — оновлювати `README.md` цього проєкту.

## 10) Definition of Done [MUST]
1. Реалізовано цільову поведінку.
2. Виконано релевантні перевірки або зафіксовано причину пропуску.
3. Оновлено docs, якщо релевантно.
4. Зафіксовано ризики/компроміси, якщо є.

## ✍️ ПРАВИЛО ЕВОЛЮЦІЇ ЦЬОГО ФАЙЛУ
Нові правила додаються так, щоб одночасно зберігати:
1. **100% змістовність та однозначність вимог**;
2. **мінімально необхідний обсяг тексту** (без дублювання, без повторів прикладів, без зайвої риторики);
3. **структурну компактність** (короткі норми, згруповані в секції, без роздування файлу).

При оновленні правил заборонено:
- видаляти чинні вимоги без явного рішення користувача;
- додавати дублікати правил у різних секціях;
- замінювати норми на розмиті формулювання, що знижують однозначність.

## 🪞 СИНХРОНІЗАЦІЯ `AGENTS.md`, `.cursorrules` І `CLAUDE.md`
- `AGENTS.md`, `.cursorrules` і `CLAUDE.md` мають бути ідентичними.
- Кожну зміну правил дублювати в усі три файли в одному оновленні.
- Після змін перевіряти: `cmp -s AGENTS.md .cursorrules && cmp -s AGENTS.md CLAUDE.md`.
