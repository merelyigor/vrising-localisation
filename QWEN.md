# vrising-localisation: коротка карта для AI-агента

Це карта обов'язкових дій, а не енциклопедія. Повний нормативний довідник:
[`docs/AI_AGENT_RULES_REFERENCE.md`](docs/AI_AGENT_RULES_REFERENCE.md).

Карта не має власної нумерації: `§N.M` завжди означає правило з довідника.
Читай із довідника **лише ту секцію**, на яку тебе відправила таблиця маршрутизації.
Відповідь власнику — українською; код, ідентифікатори, логи й тексти помилок не перекладати.

## 1. Пріоритет і стоп-умови

1. Вказівка власника в поточній задачі має пріоритет над усім, крім безпекових і юридичних обмежень.
2. Не вигадуй файл, шлях, клас, API, ENV-змінну, поле БД, команду або результат перевірки. Спочатку факт: `rg`, targeted read, лог, тест.
3. Після ДВОХ однакових невдалих спроб зупинись, назви причину і зміни підхід. Третя ідентична спроба заборонена.
4. Зупинись і попроси рішення власника, якщо: вимога суперечить правилам, ціль суттєво неоднозначна, потрібен новий дозвіл або дія необоротна.
5. Не розширюй задачу рефакторингом, новою залежністю чи новою абстракцією без конкретної потреби.

## 2. Незмінні заборони

- `git commit`, `git push`, force/rebase/tag і будь-яка зміна історії чи віддаленого стану — лише за разовим явним дозволом власника.
- Production за замовчуванням **read-only**. Правильний шлях змін: локально → перевірка → commit → штатний deploy інфри.
- SSH на прод — лише `ssh_with_password_fallback` зі `scripts/utils.sh` інфри; не прямий `ssh`, не `sshpass`. `scp`/`rsync`/редагування файлів на сервері — лише з дозволу.
- Видалення файлів і директорій, зупинка або перезапуск сервісів — лише після явного дозволу.
- Не хардкодити секрети, не виводити їх у логи, відповіді чи фронтенд-бандли.
- `docker/.env` — похідний файл; вручну не редагувати. Змінні — в `../docker/.env.local` і `../docker/.env.prod`.
- Не змінювати `usernames_translation_priority` у `core/RequestsCrowdin.php` без явного запиту: воно визначає, чиї переклади показує інструмент.
- Не робити масові або циклічні запити до Crowdin: сервіс rate-limited, результат кешувати в `json-local/`.
- Не копіювати наявний хардкод `API_KEY` у нові місця: нову інтеграцію писати проти ENV.
- Не чіпати чужі незакомічені зміни: перед стартом і перед фіналом звіряти `git status --short` і власний diff.

## 3. Обов'язковий цикл роботи

1. `bash scripts/agent-check.sh preflight` — стан дерева, середовище, ідентичність правил.
2. Сформулюй ОДНУ ціль і Definition of Done. Велику задачу розбий на перевірювані кроки.
3. Знайди факти: реалізацію, всі call sites (`rg`), конфіг, наявні тести. Поведінку не вгадуй.
4. Прочитай документи лише своєї категорії з таблиці нижче.
5. Зроби найменшу цілісну зміну. Спочатку доведи її одним реальним прикладом або найвужчою перевіркою.
6. Для виправленого поведінкового бага додай regression-перевірку. Запусти профіль своєї категорії.
7. Переглянь власний diff: секрети, generated files, `tmp-*`, зміни поза scope, чужі правки.

## 4. Маршрутизація: що читати і який gate запускати

| Що змінюєш | Прочитати ДО зміни | Gate |
|---|---|---|
| PHP-бекенд, `core/*.php` | §3 довідника; фактичний flow `api.core.php` | `agent-check.sh php` |
| Інтеграцію з Crowdin | §5 довідника; `core/RequestsCrowdin.php` | `agent-check.sh php` |
| Завантаження файлів, `save-json.php` | §6 довідника | `agent-check.sh php` |
| JS/SCSS | §8 довідника; `webpack.config.js` | `agent-check.sh frontend` |
| Правила або документацію | `docs/AI_AGENT_RULES_REFERENCE.md` (потрібна секція) | `agent-check.sh docs` |
| Docker, Nginx, env, deploy | правила інфри `merely-server-infra/AGENTS.md` | гейт інфри |
| Публічні сторінки, контент, URL | секція SEO довідника | gate + `SEO-check` у фіналі |

Якщо задача не потрапила в таблицю — знайди потрібну секцію в довіднику за його змістом.
Не завантажуй усю документацію «про всяк випадок»: це погіршує роботу слабкої моделі, а не покращує.

## 5. Quality gate

```bash
bash scripts/agent-check.sh preflight    # перед роботою, read-only
bash scripts/agent-check.sh docs         # правила, дзеркала, whitespace
bash scripts/agent-check.sh php          # php -l для змінених файлів
bash scripts/agent-check.sh frontend     # npm run build + перевірка public/assets
bash scripts/agent-check.sh full         # усе разом
```

**Заборонено повідомляти «перевірки пройшли», якщо команда не завершилась з кодом 0.**
Якщо gate неможливо запустити (немає контейнера, npm, docker) — назви точну причину,
що саме не перевірено і який це ризик. Гейт не стирає БД і не деплоїть.

## 6. Архітектура і критичні інваріанти

- Інструмент українізації V Rising: PHP-бекенд (`core/*.php`) + JS/SCSS фронт на Webpack (`src/*` → `public/assets/*`).
- **Джерело правди перекладів — Crowdin** (`PROJECT_ID = 519216`), не локальна БД: цей проєкт БД не використовує взагалі.
- `core/RequestsCrowdin.php` — обгортка над `crowdin/crowdin-api-client`; `core/api.core.php` — тонкий HTTP-роутер над GET-параметрами.
- `json-local/` — локальний кеш/експорт; `save-json.php` **безумовно перезаписує** файл із тим самим імʼям і не перевіряє тип чи розмір — це відомий борг, не приклад.
- Валідація й санітизація GET-параметрів обов'язкові для нового коду.
- Local: `localisation-vrising-ua.eremenko.dev`. Production: `localisation-vrising-ua.eremenko.top`.

## 7. Інструменти

- Serena — primary path для refactoring і references; route-параметри, Webpack і конфіги — `rg` + targeted reads (§4).
- Shadcn/UI: стек PHP + vanilla frontend **не є сумісним React/Tailwind контуром**, тому Shadcn тут не застосовується (§4).
- Context7 — доречний саме тут для API `crowdin/crowdin-api-client`, з пріоритетом версії з `composer.lock`.
- Браузер — після `php -l`, логів і прямих запитів до Crowdin API.

## 8. Слабкі та локальні моделі

Одна вузька задача за сесію з явним Definition of Done. Спочатку один реальний приклад,
потім вузька перевірка, потім повний gate. Жодного вигаданого API, поля чи результату.
Після двох однакових невдач — зміна підходу, а не третя спроба. Без необов'язкового
рефакторингу й нових залежностей. Фінально — перегляд diff на secrets і scope drift.

Довідник моделей і прийомний набір для нової моделі — в інфра-репозиторії:
`merely-server-infra/docs/AI-AGENT-MODELS.md` і `docs/AGENT-MODEL-QUALIFICATION.md`.

## 9. Фінальний звіт

Для кожної відповіді з виконаною роботою обов'язкові два окремі блоки:

1. `## Звіт` — самодостатній результат у порядку **Зроблено** → **Зʼясовано** →
   **Перевірки** → `SEO-check` → `OSM-check`.
2. У **Зʼясовано** кожен висновок має доказ: цифру, вивід команди або рядок коду;
   виправлення власної хибної заяви — окремим рядком.
3. У **Перевірки** вказувати команду й результат; невиконані перевірки — окремо,
   з причиною та ризиком.
4. Аналіз над звітом тримати коротко; звіт фіксує результат, а не переказує процес.
5. `## Що далі` — останнім: статус, 2-4 варіанти (перший рекомендований), що
   потрібно від власника, Done criteria.

Ніколи не заявляй про завершення, якщо релевантний gate не завершився з кодом 0.
